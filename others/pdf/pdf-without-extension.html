PDF at a URL with no .pdf in it

Chrome opens its PDF viewer from the response's Content-Type, not from the file name. So a PDF address does not need to end in .pdf.

Why this matters. Readalix has two ways of noticing a PDF. The content script asks the document — document.contentType — which is always right. The popup and the background match the tab address against /\.pdf(\?|#|$)/i, which every address on this page defeats. So reading is expected to work, and the popup is expected to be wrong: the pick-element button shows although a PDF tab has nothing to pick, and the note that explains that play reads from the top is missing.

A download endpoint cannot be hosted here. The shape https://example.com/download?id=8421 needs a file with no extension, and GitHub Pages then sends Content-Type: application/octet-stream (measured), which Chrome downloads instead of showing. GitHub Pages sends application/pdf only for a name that ends in .pdf — and that name matches the address test again. Use a live example for that case instead: https://arxiv.org/pdf/2401.12345 — a real PDF with no extension in its address.

Blob URL — the same gap, reproducible here

A blob address holds no file name at all: blob:https://zuhairtaha.github.io/<uuid>. Web applications use this shape often — they fetch a statement, an invoice or a report with JavaScript and open the bytes, so the address of the PDF tab is a blob address. The buttons below fetch Readalix reads PDFs.pdf from this folder and open it that way.

  • Press play with nothing selected. Expected result unknown — a content script does not run on a blob: document, so Readalix may read nothing at all. Write down what happens.
  • Select a passage, then play. Same check.
  • Compare with the control — the identical document at an ordinary .pdf address, which reads and highlights.
